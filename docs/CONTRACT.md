# Формат данных, версия 0.2

Общий язык генератора, движка и интерфейса. Меняется только по согласию обоих (Григорий и Антон).

Набор данных - один JSON-файл. Движок читает только JSON. CSV загружается через `naryad.data.csvio.read_csv`, превращается в такой же набор и проходит ту же проверку.

```
{
  "meta":     {...},
  "parks":    [...],
  "routes":   [...],
  "duties":   [...],   наряды (выходы)
  "shifts":   [...],   смены внутри нарядов
  "vehicles": [...],
  "drivers":  [...]
}
```

Один файл - один день. Генератор выдаёт серию таких файлов подряд: постоянная часть (парки, маршруты, наряды, автобусы и водители как люди) в них одинаковая, меняется только состояние дня (исправность, график, медосмотр).

Время записывается как `ЧЧ:ММ` от начала суток. После полуночи часы идут дальше 24: `25:10` - это 01:10 следующего дня.

## Кто что заполняет

| Что | Кто |
|---|---|
| Исправен / неисправен, срок ремонта, график водителя, больничный, отпуск, медосмотр | Генератор (в жизни - парк) |
| Какой автобус и водитель на каком наряде | **Движок** |
| Группы «на маршруте / резерв / исправен в парке / неисправен» | Считаются из плана движка, показывает интерфейс |

Генератор никогда не ставит автобус на наряд: иначе движку нечего решать.

|---|---|---|

## Проверка

`naryad.data.check.check(data)` возвращает `{"errors": [...], "warnings": [...]}`.

- **Ошибка** - данные противоречат сами себе (повтор номера, ссылка в никуда, смены не встык, список автобусов не сходится с `list_count`). Движку такие данные не отдаём.
- **Предупреждение** - данные целы, но расходятся с планом или не хватает автобусов либо водителей. Это рабочая ситуация, её и решает движок.

## План - ответ движка (версия 0.3, согласовано Григорием и Антоном 02.10.2026)

Отдельный JSON рядом с набором данных дня. Генератор его не создаёт, его выдаёт движок или правит диспетчер.

```
{
  "meta":                {"made_by": "engine", ...},
  "vehicle_assignments": [{"duty_id": "P07-R01-WD01", "vehicle_id": "P07-V0001"}, ...],
  "driver_assignments":  [{"shift_id": "P07-R01-WD01-S1", "driver_id": "P07-D0001"}, ...],
  "unfilled":            [{"id": "P07-R12-WD04", "reason": "no_vehicle"}, ...],
  "transfers":           [{"vehicle_id": "P01-V0123", "to_park": "P03"}, ...]
}
```

| Поле | Что это |
|---|---|
| vehicle_assignments | Какой автобус на каком наряде. Один наряд - не больше одного автобуса |
| driver_assignments | Какой водитель на какой смене. Водитель ставится только на смену наряда, у которого есть автобус |
| unfilled | Что осталось незакрытым и почему: id наряда (нет автобуса) или смены (нет водителя) |
| transfers | Переброски на день: автобус из одного парка работает на нарядах другого. Без записи здесь автобус чужого парка на наряде - нарушение |

Причины незакрытого (`reason`):

| Код | Что значит |
|---|---|
| no_vehicle | Нет исправного автобуса нужного класса |
| no_driver | Нет водителя с допуском, который работает в этот день |
| release_limit | Выпуск парка исчерпан |
| lower_priority | Ресурс отдан маршрутам важнее |
| park_down | Парк не выпускает автобусы |
| manual | Решение диспетчера |

Проверка плана: `naryad.core.invariants.check_plan(day, plan)` возвращает список нарушений. Пустой список - план можно выпускать. Незакрытый наряд с причиной - не нарушение, а честный план. Нормы труда для проверки лежат в `naryad/core/labor.json` вместе с источником и статусом каждой цифры.

## Объяснения для интерфейса (согласовано Григорием и Антоном 02.10.2026)

Модуль `naryad.explain`. Каждая функция возвращает словарь, который интерфейс показывает как есть:

```
{
  "question": "Почему наряд P07-R17-WD18 (маршрут 141) не закрыт?",
  "answer":   "Не хватило автобусов класса «большой»: исправны 196, все 196 заняты",
  "reasons":  ["Не вышли: 11 на ТО, 51 в ремонте", "Интервал в 11:32: по плану 7 мин, сейчас 8 мин", ...],
  "numbers":  {"vehicles_ok": 196, "vehicles_busy": 196, "planned_min": 7, "actual_min": 8, ...}
}
```

| Функция | Вопрос диспетчера |
|---|---|
| `why_vehicle(day, plan, duty_id)` | Почему на наряде этот автобус |
| `why_driver(day, plan, shift_id, history)` | Почему на смене этот водитель, и что с закреплёнными |
| `why_unfilled(day, plan, id)` | Почему наряд или смена не закрыты |
| `explain_option(state, event, options, i)` | Что даст вариант замены и чем он лучше следующего |
| `day_summary(day, plan)` | Сводка дня: что закрыто, где сосредоточены пустые наряды и смены |
| `interval(day, plan, route_id, t)` | Интервал на маршруте в момент t: по плану и фактический |

`answer` - одна фраза для карточки, `reasons` - пункты под ней, `numbers` - те же цифры для таблиц и графиков.

## Состояние дня (версия 0.1, предложение Григория 02.10.2026, ждёт согласия Антона)

Утренний план отвечает «какой автобус на каком наряде весь день». После схода, ДТП или неявки на одном наряде за день бывает два автобуса и два водителя, поэтому внутри дня движок держит **состояние**: отрезки «с какого по какое время кто». План из раздела выше - частный случай состояния с одним отрезком на наряд. Интерфейс рисует именно состояние.

```
{
  "meta":     {"day_id": "day-1", "date": "2026-10-05", "events": 1, "labor": "current"},
  "duties":   [{"duty_id": "P07-R01-WD01",
                "vehicles": [{"from": "04:50", "to": "08:40", "vehicle_id": "P07-V0038"},
                             {"from": "09:10", "to": "25:20", "vehicle_id": "P07-V0117"}]}, ...],
  "shifts":   [{"shift_id": "P07-R01-WD01-S1",
                "drivers":  [{"from": "04:50", "to": "08:40", "driver_id": "P07-D0603"},
                             {"from": "09:10", "to": "11:40", "driver_id": "P07-D0131"}]}, ...],
  "unfilled": [{"id": "P07-R12-WD04", "reason": "no_vehicle"}, ...],
  "transfers": [{"vehicle_id": "P01-V0123", "to_park": "P03"}, ...],
  "down_vehicles": [{"vehicle_id": "P07-V0038", "since": "08:40"}],
  "down_drivers":  [{"driver_id": "P07-D0412", "since": "04:30"}],
  "log": [{"at": "08:40", "type": "breakdown", "vehicle_id": "P07-V0038", "duration_min": null,
           "option": 1, "title": "Резерв: автобус 7117"}]
}
```

| Поле | Что это |
|---|---|
| duties | Только наряды, у которых есть автобус хотя бы на часть дня. Отрезки идут по времени, между ними могут быть разрывы: автобус сошёл в 08:40, замена подана в 09:10 |
| shifts | То же для водителей на сменах |
| unfilled, transfers | Как в плане |
| down_vehicles, down_drivers | Кто выбыл за день и с какого времени. Автобус после схода на время сюда не попадает |
| log | События дня по порядку: событие в том виде, как его прислал интерфейс, номер выбранного варианта и его название |

Проверка состояния: `naryad.ops.replan.check_state(state)` - те же правила, что `check_plan`, плюс «автобус не может быть на двух нарядах в один момент» по отрезкам.

## API движка (версия 0.1, предложение Григория 02.10.2026, ждёт согласия Антона)

Код - `naryad/web/api.py`, без сторонних библиотек. Пока страница генератора не подключила модуль, API поднимается отдельно: `python -m naryad.web.api`, порт 8001, с заголовками CORS, чтобы страница с порта 8000 звала его напрямую. Единственная точка входа - `Engine.handle(метод, адрес, параметры, тело)`, сервер страницы сможет звать её без HTTP. Все ответы - JSON в UTF-8. Ошибка - `{"error": "текст по-русски"}` с кодом 400 (неверный запрос), 404 (нет такого дня, наряда, смены) или 409 (действие раньше времени: объяснение или событие до того, как построен план).

Сервер держит загруженные дни в памяти под номерами `day_id` и ничего не пишет на диск: перезапуск сервера стирает дни. Всё, что отдаёт API, восстанавливается из дня, плана и журнала событий. Набор норм труда задаётся при запуске (`--labor likely` или `NARYAD_LABOR`) и один на весь сервер.

Время везде строкой `ЧЧ:ММ`, после полуночи часы идут дальше 24 (`25:20`), как в данных дня.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/labor` | Нормы труда: значение, правило, пункт Приказа № 160, статус каждой цифры, действующий набор |
| `GET /api/days` | Загруженные дни: `day_id`, дата, тип дня, построен ли план, сколько событий |
| `POST /api/days` | Загрузить день: JSON дня целиком или `{"preset", "date", "seed", "moment"}` для генератора |
| `GET /api/days/{day_id}` | День как есть (JSON из раздела «Формат данных») - интерфейсу для списков и карточек |
| `POST /api/days/{day_id}/plan` | Построить утренний план: автобусы, потом водители. Тело пустое или `{"history_from": "day-0"}` |
| `GET /api/days/{day_id}/state` | Состояние дня (раздел выше). До событий совпадает с планом |
| `GET /api/days/{day_id}/explain/vehicle/{duty_id}` | Почему на наряде этот автобус |
| `GET /api/days/{day_id}/explain/driver/{shift_id}` | Почему на смене этот водитель |
| `GET /api/days/{day_id}/explain/unfilled/{id}` | Почему наряд или смена не закрыты |
| `GET /api/days/{day_id}/explain/summary` | Сводка дня |
| `GET /api/days/{day_id}/explain/interval/{route_id}?t=08:30` | Интервал на маршруте в момент t |
| `POST /api/days/{day_id}/events/options` | Варианты замены на событие, ничего не меняет |
| `POST /api/days/{day_id}/events/apply` | Применить выбранный вариант, вернуть новое состояние |
| `GET /api/days/{day_id}/log` | Журнал событий и решений за день |

### POST /api/days - загрузить день

Тело - либо JSON дня целиком (`{"meta": ..., "parks": ..., ...}`), либо вводные для генератора:

```
{"preset": "park7", "date": "2026-10-05", "seed": 1, "moment": "morning"}
```

День проходит `naryad.data.check.check`. С ошибками день не принимается (400, в ответе список ошибок); предупреждения не мешают, это рабочая ситуация, которую и решает движок.

```
{
  "day_id": "day-1",
  "date": "2026-10-05", "day_type": "weekday", "moment": "morning", "preset": "park7",
  "counts": {"parks": 1, "routes": 24, "duties": 350, "shifts": 717, "vehicles": 420, "drivers": 1315},
  "warnings": []
}
```

`warnings` - строки из `naryad.data.check` как есть, например о нехватке автобусов под выпуск; у образца парка №7 их нет.

### POST /api/days/{day_id}/plan - построить план

Тело пустое или `{"history_from": "day-0"}`: водители помнят прошлые дни (отдых, часы за месяц), `day-0` - день с построенным планом, идущий накануне. Повторный вызов строит план заново и стирает события дня.

```
{
  "plan": { ...раздел «План - ответ движка»... },
  "violations": [],
  "summary": { ...day_summary, раздел «Объяснения»... },
  "seconds": 0.27
}
```

`violations` - нарушения из `check_plan`, у движка их не бывает; поле есть, чтобы интерфейс показывал результат проверки для планов, которые правил диспетчер:

```
[{"code": "driver_overtime", "text": "Водитель 070562: 10 ч 15 мин за день, норма 10 ч 00 мин", "ids": ["P07-D0562"]}]
```

### GET .../explain/... - объяснения

Ответ - словарь из раздела «Объяснения для интерфейса» без изменений. Для `interval` обязателен параметр `t` в виде `ЧЧ:ММ`. Если план ещё не построен - 409. Если наряд закрыт, `explain/unfilled` отвечает 404 с текстом «наряд закрыт, смотрите explain/vehicle».

### POST /api/days/{day_id}/events/options - варианты на событие

Событие - одно из трёх:

```
{"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40", "duration_min": 20}   сход; без duration_min - насовсем
{"type": "accident",  "vehicle_id": "P07-V0038", "at": "17:30"}                       ДТП, автобус выбывает насовсем
{"type": "no_show",   "driver_id":  "P07-D0412", "at": "04:30"}                       неявка или недопуск на медосмотре
```

Ответ: до трёх лучших вариантов разных видов, первый - лучший по цене, плюс вариант «не заменять» для сравнения.

```
{
  "event": {"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40", "duration_min": null},
  "options": [
    {"index": 0, "kind": "idle", "title": "Автобус из парка 7197 + водитель 070540",
     "cost": 1.14, "lost_minutes": 30,
     "note": "подача из парка ~30 мин, резерв не тратится",
     "explanation": {"question": "Что даст вариант «Автобус из парка 7197 + водитель 070540»?", "answer": "...", "reasons": [...], "numbers": {...}}},
    {"index": 1, "kind": "reserve", "title": "Резерв: автобус 7117", "cost": 2.52, "lost_minutes": 30, "note": "...", "explanation": {...}},
    {"index": 2, "kind": "donor", "title": "Снять автобус 7228 с маршрута 39Э", "cost": 8.56, "lost_minutes": 315, "note": "...", "explanation": {...}}
  ]
}
```

| Поле | Что это |
|---|---|
| kind | Вид варианта: `none` не заменять, `idle` исправный автобус из парка сверх выпуска, `reserve` резервный наряд, `donor` автобус с менее важного маршрута, `free_driver` свободный водитель на смену |
| cost | Цена в единицах движка: часы простоя на линии с весом важности маршрута и штрафом за рост интервала. Меньше - лучше, сравнивать только внутри одного ответа |
| lost_minutes | Сколько минут линия стоит без автобуса на всех затронутых маршрутах |
| explanation | `explain_option` для этого варианта: чем он лучше следующего |

Если автобуса нет на линии в этот момент или водителя нет на смене - 400 с текстом.

### POST /api/days/{day_id}/events/apply - применить вариант

```
{"event": {"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40"}, "option": 1}
```

Сервер заново строит варианты на это событие (они детерминированы), применяет вариант с номером `option` и отвечает состоянием дня (раздел «Состояние дня») с полем `violations` из `check_state`. События применяются только по порядку времени: событие раньше последнего в журнале - 400.
