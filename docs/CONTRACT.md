# Формат данных, версия 0.2

Общий язык генератора, движка и интерфейса. Меняется только по согласию обоих (Григорий и Антон).

Набор данных - один JSON-файл. Движок читает только JSON. CSV загружается через `naryad.data.csvio.read_csv`, превращается в такой же набор и проходит ту же проверку.

```
{
  "meta":     {...},
  "parks":    [...],
  "routes":   [...],
  "duties":   [...],   наряды (выходы)
  "shifts":   [...],   смены внутри нарядов
  "vehicles": [...],
  "drivers":  [...]
}
```

Один файл - один день. Генератор выдаёт серию таких файлов подряд: постоянная часть (парки, маршруты, наряды, автобусы и водители как люди) в них одинаковая, меняется только состояние дня (исправность, график, медосмотр).

Время записывается как `ЧЧ:ММ` от начала суток. После полуночи часы идут дальше 24: `25:10` - это 01:10 следующего дня.

## Кто что заполняет

| Что | Кто |
|---|---|
| Исправен / неисправен, срок ремонта, график водителя, больничный, отпуск, медосмотр | Генератор (в жизни - парк) |
| Какой автобус и водитель на каком наряде | **Движок** |
| Группы «на маршруте / резерв / исправен в парке / неисправен» | Считаются из плана движка, показывает интерфейс |

Генератор никогда не ставит автобус на наряд: иначе движку нечего решать.

## meta

| Поле | Пример | Что это |
|---|---|---|
| format_version | `"0.1"` | Версия этого описания |
| preset | `"case"` / `"park7"` | Вводные кейса или реальный парк №7 |
| inputs | `{"park_count": 7, ...}` | Вводные, по которым построен город |
| seed | `1` | Номер набора: одинаковый номер даёт одинаковые данные |
| date | `"2026-10-05"` | Дата дня |
| day_index | `0` | Номер дня в серии, с нуля |
| day_type | `"weekday"` / `"weekend"` | Будни или выходной |
| moment | `"plan"` / `"morning"` | План на завтра (медосмотр ещё не проходили) или утро дня |
| source, assumptions | | Откуда цифры и что додумано |

`date` и `day_type` обязательны: без них день нельзя ни спланировать, ни показать, и проверка такой набор не пропустит. `moment`, если он есть, может быть только `plan` или `morning`.

## Проверка

`naryad.data.check.check(data)` возвращает `{"errors": [...], "warnings": [...]}`.

- **Ошибка** - данные противоречат сами себе (нет блока `meta` с датой и типом дня, повтор номера, ссылка в никуда, смены не встык, список автобусов не сходится с `list_count`, важность маршрута не 1, 2 или 3, наряд и его маршрут из разных парков, водитель закреплён за автобусом другого парка, ни одного наряда на заявленный тип дня). Движку такие данные не отдаём.
- **Предупреждение** - данные целы, но расходятся с планом или не хватает автобусов либо водителей, либо парк не выпускает автобусы при наличии нарядов. Это рабочая ситуация, её и решает движок.

## План - ответ движка (версия 0.3, согласовано Григорием и Антоном 02.10.2026)

Отдельный JSON рядом с набором данных дня. Генератор его не создаёт, его выдаёт движок или правит диспетчер.

```
{
  "meta":                {"made_by": "engine", ...},
  "vehicle_assignments": [{"duty_id": "P07-R01-WD01", "vehicle_id": "P07-V0001"}, ...],
  "driver_assignments":  [{"shift_id": "P07-R01-WD01-S1", "driver_id": "P07-D0001"}, ...],
  "unfilled":            [{"id": "P07-R12-WD04", "reason": "no_vehicle"}, ...],
  "transfers":           [{"vehicle_id": "P01-V0123", "to_park": "P03"}, ...]
}
```

| Поле | Что это |
|---|---|
| vehicle_assignments | Какой автобус на каком наряде. Один наряд - не больше одного автобуса |
| driver_assignments | Какой водитель на какой смене. Водитель ставится только на смену наряда, у которого есть автобус |
| unfilled | Что осталось незакрытым и почему: id наряда (нет автобуса) или смены (нет водителя) |
| transfers | Переброски на день: автобус из одного парка работает на нарядах другого. Без записи здесь автобус чужого парка на наряде - нарушение |

Причины незакрытого (`reason`):

| Код | Что значит |
|---|---|
| no_vehicle | Нет исправного автобуса нужного класса |
| no_driver | Нет водителя с допуском, который работает в этот день |
| release_limit | Выпуск парка исчерпан |
| lower_priority | Ресурс отдан маршрутам важнее |
| park_down | Парк не выпускает автобусы |
| manual | Решение диспетчера |

Проверка плана: `naryad.core.invariants.check_plan(day, plan)` возвращает список нарушений. Пустой список - план можно выпускать. Незакрытый наряд с причиной - не нарушение, а честный план. Нормы труда для проверки лежат в `naryad/core/labor.json` вместе с источником и статусом каждой цифры.

## Объяснения для интерфейса (согласовано Григорием и Антоном 02.10.2026)

Модуль `naryad.explain`. Каждая функция возвращает словарь, который интерфейс показывает как есть:

```
{
  "question": "Почему наряд P07-R17-WD18 (маршрут 141) не закрыт?",
  "answer":   "Не хватило автобусов класса «большой»: исправны 196, все 196 заняты",
  "reasons":  ["Не вышли: 11 на ТО, 51 в ремонте", "Интервал в 11:32: по плану 7 мин, сейчас 8 мин", ...],
  "numbers":  {"vehicles_ok": 196, "vehicles_busy": 196, "planned_min": 7, "actual_min": 8, ...}
}
```

| Функция | Вопрос диспетчера |
|---|---|
| `why_vehicle(day, plan, duty_id)` | Почему на наряде этот автобус |
| `why_driver(day, plan, shift_id, history)` | Почему на смене этот водитель, и что с закреплёнными |
| `why_unfilled(day, plan, id)` | Почему наряд или смена не закрыты |
| `explain_option(state, event, options, i)` | Что даст вариант замены и чем он лучше следующего |
| `day_summary(day, plan)` | Сводка дня: что закрыто, где сосредоточены пустые наряды и смены |
| `interval(day, plan, route_id, t)` | Интервал на маршруте в момент t: по плану и фактический |

`answer` - одна фраза для карточки, `reasons` - пункты под ней, `numbers` - те же цифры для таблиц и графиков.

## Состояние дня (версия 0.2, предложение Григория 02.10.2026, ручная правка добавлена 05.10.2026, ждёт согласия Антона)

Утренний план отвечает «какой автобус на каком наряде весь день». После схода, ДТП или неявки на одном наряде за день бывает два автобуса и два водителя, поэтому внутри дня движок держит **состояние**: отрезки «с какого по какое время кто». План из раздела выше - частный случай состояния с одним отрезком на наряд. Интерфейс рисует именно состояние.

```
{
  "meta":     {"day_id": "day-1", "date": "2026-10-05", "events": 1, "edits": 0, "labor": "current"},
  "duties":   [{"duty_id": "P07-R01-WD01",
                "vehicles": [{"from": "04:50", "to": "08:40", "vehicle_id": "P07-V0038"},
                             {"from": "09:10", "to": "25:20", "vehicle_id": "P07-V0117"}]}, ...],
  "shifts":   [{"shift_id": "P07-R01-WD01-S1",
                "drivers":  [{"from": "04:50", "to": "08:40", "driver_id": "P07-D0603"},
                             {"from": "09:10", "to": "11:40", "driver_id": "P07-D0131"}]}, ...],
  "unfilled": [{"id": "P07-R12-WD04", "reason": "no_vehicle"}, ...],
  "transfers": [{"vehicle_id": "P01-V0123", "to_park": "P03"}, ...],
  "down_vehicles": [{"vehicle_id": "P07-V0038", "since": "08:40"}],
  "down_drivers":  [{"driver_id": "P07-D0412", "since": "04:30"}],
  "log": [{"kind": "event", "at": "08:40", "type": "breakdown", "vehicle_id": "P07-V0038",
           "duration_min": null, "option": 1, "title": "Резерв: автобус 7117"}]
}
```

| Поле | Что это |
|---|---|
| duties | Только наряды, у которых есть автобус хотя бы на часть дня. Отрезки идут по времени, между ними могут быть разрывы: автобус сошёл в 08:40, замена подана в 09:10 |
| shifts | То же для водителей на сменах |
| unfilled | Незакрытое на этот момент, а не утром. Наряд, который диспетчер закрыл вручную, из списка уходит; наряд, с которого он снял автобус, попадает с причиной `removed_by_dispatcher`. Причины из плана: `no_vehicle`, `no_driver`, `park_down`, `release_limit`. Смены резервных нарядов, которым движок не ставил водителя, сюда не попадают: они не незакрыты, они не нужны |
| transfers | Как в плане |
| down_vehicles, down_drivers | Кто выбыл за день и с какого времени. Автобус после схода на время сюда не попадает |
| log | Журнал дня по порядку: события и ручные правки диспетчера вместе. `kind` - `event` или `edit`. У события - оно само в том виде, как его прислал интерфейс, номер выбранного варианта и его название; у правки - поля правки, `forced` и список нарушений, на которые диспетчер пошёл сознательно. `meta.events` и `meta.edits` считают их по отдельности |

Проверка состояния: `naryad.ops.replan.check_state(state)` возвращает такие же нарушения, как `check_plan` (код, текст, id), и там, где правило то же, тем же кодом. Правила по отрезкам у неё свои: отрезок внутри времени наряда и непустой (`bad_segment`), два отрезка не перекрываются (`segment_overlap`), ресурс не стоит после выбытия (`down_but_working`). Четырёх правил утренней проверки в ней нет, и это осознанно: лимит выпуска парка и состояние парка внутри дня проверять нечему, варианты замены только переставляют автобусы между уже выпущенными нарядами; «одна смена на водителя в день» внутри дня не действует, потому что водитель резерва законно появляется и на своём резервном наряде, и на линии, а длину его рабочего дня проверяет `driver_overtime`; «водитель только на наряде с автобусом» запретило бы законный вариант «не заменять», когда автобус сошёл, а водитель ждёт пересменки.

## API движка (версия 0.3, предложение Григория 02.10.2026, ручная правка и загрузка реестров добавлены 05.10.2026, ждёт согласия Антона)

Код - `naryad/web/api.py`, без сторонних библиотек. Пока страница генератора не подключила модуль, API поднимается отдельно: `python -m naryad.web.api`, порт 8001. Заголовок `Access-Control-Allow-Origin` выдаётся только страницам с этого же компьютера (`localhost`, `127.0.0.1`, `[::1]` с любым портом): день целиком - это реестр перевозчика, и любой открытой в браузере странице его отдавать нельзя. Предварительный запрос с чужого адреса получает 403. Единственная точка входа - `Engine.handle(метод, адрес, параметры, тело)`, сервер страницы сможет звать её без HTTP. Все ответы - JSON в UTF-8. Ошибка - `{"error": "текст по-русски"}` с кодом 400 (неверный запрос), 404 (нет такого дня, наряда, смены), 405 (не тот метод), 409 (в этом состоянии не выполняется: объяснение или событие до того, как построен план; ручная правка, которая нарушает нормы, без `force`) или 500 (ошибка самого движка: ответ `{"error": "Внутренняя ошибка сервиса...", "kind": "ИмяОшибки"}`, трассировка уходит только в журнал сервера).

Правило для всех ручек: сначала проверяется весь запрос, потом считается, и только потом меняется память. Отклонённый запрос ничего не меняет: план, состояние дня, журнал и память водителей остаются такими, какими их видит диспетчер.

Сервер держит загруженные дни в памяти под номерами `day_id` и ничего не пишет на диск: перезапуск сервера стирает дни. Всё, что отдаёт API, восстанавливается из дня, плана и журнала событий. Набор норм труда задаётся при запуске (`--labor likely` или `NARYAD_LABOR`) и один на весь сервер.

Время везде строкой `ЧЧ:ММ`, после полуночи часы идут дальше 24 (`25:20`), как в данных дня.

| Метод и адрес | Что делает |
|---|---|
| `GET /api/labor` | Нормы труда: значение, правило, пункт Приказа № 160, статус каждой цифры, действующий набор |
| `GET /api/days` | Загруженные дни: `day_id`, дата, тип дня, построен ли план, сколько событий и сколько ручных правок |
| `POST /api/days` | Загрузить день: JSON дня целиком или `{"preset", "date", "seed", "moment"}` для генератора |
| `POST /api/days/import` | Загрузить день из реестра перевозчика: CSV текстом или книга Excel в base64 |
| `GET /api/days/{day_id}` | День как есть (JSON из раздела «Формат данных») - интерфейсу для списков и карточек |
| `POST /api/days/{day_id}/plan` | Построить утренний план: автобусы, переброски между парками, потом водители |
| `GET /api/days/{day_id}/state` | Состояние дня (раздел выше). До событий и правок совпадает с планом |
| `GET /api/days/{day_id}/explain/vehicle/{duty_id}` | Почему на наряде этот автобус |
| `GET /api/days/{day_id}/explain/driver/{shift_id}` | Почему на смене этот водитель |
| `GET /api/days/{day_id}/explain/unfilled/{id}` | Почему наряд или смена не закрыты |
| `GET /api/days/{day_id}/explain/summary` | Сводка дня |
| `GET /api/days/{day_id}/explain/interval/{route_id}?t=08:30` | Интервал на маршруте в момент t, в том же виде `question / answer / reasons / numbers`, что остальные объяснения |
| `POST /api/days/{day_id}/events/options` | Варианты замены на событие, ничего не меняет |
| `POST /api/days/{day_id}/events/apply` | Применить выбранный вариант, вернуть новое состояние |
| `GET /api/days/{day_id}/edits/options` | Кого законно можно поставить на наряд или смену, ничего не меняет |
| `POST /api/days/{day_id}/edits` | Ручная правка плана диспетчером: поставить или снять автобус, водителя |
| `GET /api/days/{day_id}/log` | Журнал дня: события и ручные правки по порядку |

### POST /api/days - загрузить день

Тело - либо JSON дня целиком (`{"meta": ..., "parks": ..., ...}`), либо вводные для генератора:

```
{"preset": "park7", "date": "2026-10-05", "seed": 1, "moment": "morning"}
```

День проходит `naryad.data.check.check`. С ошибками день не принимается (400, в ответе список ошибок); предупреждения не мешают, это рабочая ситуация, которую и решает движок.

```
{
  "day_id": "day-1",
  "date": "2026-10-05", "day_type": "weekday", "moment": "morning", "preset": "park7",
  "counts": {"parks": 1, "routes": 24, "duties": 350, "shifts": 717, "vehicles": 420, "drivers": 1315},
  "warnings": []
}
```

`warnings` - строки из `naryad.data.check` как есть, например о нехватке автобусов под выпуск; у образца парка №7 их нет.

### POST /api/days/{day_id}/plan - построить план

Тело пустое или с любым из полей:

| Поле | Пример | Что делает |
|---|---|---|
| history_from | `"day-0"` | Водители помнят прошлые дни (отдых, часы за месяц). `day-0` - день с построенным планом, идущий накануне. Без него водители считаются отдохнувшими |
| transfers | `false` | Перебрасывать ли лишние исправные автобусы из одного парка в другой (А7). По умолчанию включено, когда в дне больше одного парка: одному парку перебрасывать некуда |
| gas_parks | `["P03", "P05", "P07"]` | Парки с газовой инфраструктурой: только туда можно отдать газовый автобус. Без этого поля ограничения нет, потому что в данных генератора признака газа у парка нет. Неизвестный номер парка - 404 |

Повторный вызов строит план заново и стирает события дня.

```
{
  "plan": { ...раздел «План - ответ движка»... },
  "violations": [],
  "rest_violations": [],
  "summary": { ...day_summary, раздел «Объяснения»... },
  "notes": [],
  "seconds": 0.27
}
```

| Поле | Что это |
|---|---|
| violations | Нарушения в самом плане этого дня (`check_plan`) |
| rest_violations | Нарушения норм отдыха между сменами и днями (`check_rest`, п. 16, 17, 20 Приказа № 160). Считаются по всем дням этого же набора данных, которые уже загружены и спланированы, по порядку дат: тот же состав парков, та же настройка, тот же номер набора. День другого города не считается предыдущей сменой, даже если номера водителей совпали |
| notes | Замечания по порядку работы, не нарушения: не передан `history_from`, хотя более ранний день уже спланирован; память водителей взята по дню, в котором были события |
| seconds | Сколько заняла расстановка |

Пустой `rest_violations` значит ровно одно: по тем дням, которые загружены в сервис, нормы отдыха соблюдены. Что было до первого загруженного дня, сервис не знает и считает, что перед ним у всех был еженедельный отдых.

Переброски видны в плане и в состоянии дня полем `transfers`: автобус чужого парка на наряде без такой записи - нарушение, его ловит `check_plan`.

`violations` - нарушения из `check_plan`. У утреннего плана движка их не бывает, но поле проверяется каждый раз: оно же показывает результат для планов, которые правил диспетчер, и для данных, пришедших извне. Пустой список не означает, что соблюдены нормы отдыха между днями: их считает `check_rest`, и они приходят отдельным полем `rest_violations`.

```
[{"code": "driver_overtime", "text": "Водитель 070562: 10 ч 15 мин за день, норма 10 ч 00 мин", "ids": ["P07-D0562"]}]
```

### GET .../explain/... - объяснения

Ответ - словарь из раздела «Объяснения для интерфейса» без изменений: четыре поля `question`, `answer`, `reasons`, `numbers`. Для `interval` обязателен параметр `t` в виде `ЧЧ:ММ`, а измеренные числа лежат в `numbers` (`planned_min`, `actual_min`, `planned_buses`, `running_buses`). Если план ещё не построен - 409. Если наряд закрыт, `explain/unfilled` отвечает 404 с текстом «наряд закрыт, смотрите explain/vehicle».

### POST /api/days/{day_id}/events/options - варианты на событие

Событие - одно из трёх:

```
{"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40", "duration_min": 20}   сход; без duration_min - насовсем
{"type": "accident",  "vehicle_id": "P07-V0038", "at": "17:30"}                       ДТП, автобус выбывает насовсем
{"type": "no_show",   "driver_id":  "P07-D0412", "at": "04:30"}                       неявка или недопуск на медосмотре
```

Ответ: до трёх лучших вариантов разных видов, первый - лучший по цене, плюс вариант «не заменять» для сравнения. Он в ответе всегда, даже когда дороже остальных и не попал в лучшие: диспетчеру нужна точка отсчёта. Поэтому вариантов бывает до четырёх.

```
{
  "event": {"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40", "duration_min": null},
  "options": [
    {"index": 0, "kind": "idle", "title": "Автобус из парка 7197 + водитель 070540",
     "cost": 1.14, "lost_minutes": 30,
     "note": "подача из парка ~30 мин, резерв не тратится",
     "explanation": {"question": "Что даст вариант «Автобус из парка 7197 + водитель 070540»?", "answer": "...", "reasons": [...], "numbers": {...}}},
    {"index": 1, "kind": "reserve", "title": "Резерв: автобус 7117", "cost": 2.52, "lost_minutes": 30, "note": "...", "explanation": {...}},
    {"index": 2, "kind": "donor", "title": "Снять автобус 7228 с маршрута 39Э", "cost": 8.56, "lost_minutes": 315, "note": "...", "explanation": {...}}
  ]
}
```

| Поле | Что это |
|---|---|
| kind | Вид варианта: `none` не заменять, `idle` исправный автобус из парка сверх выпуска, `reserve` резервный наряд, `donor` автобус с менее важного маршрута, `free_driver` свободный водитель на смену, `reserve_driver` водитель резервного наряда на смену линии |
| cost | Цена в единицах движка: часы простоя на линии с весом важности маршрута и штрафом за рост интервала. Меньше - лучше, сравнивать только внутри одного ответа |
| lost_minutes | Сколько минут линия стоит без автобуса на всех затронутых маршрутах |
| explanation | `explain_option` для этого варианта: чем он лучше следующего |

Если автобуса нет на линии в этот момент или водителя нет на смене - 400 с текстом.

Замена ищется только внутри парка наряда: переброска между парками - решение утренней нарядки на весь день (поле `transfers` плана), внутри дня она не пересматривается. Интерфейсу не стоит обещать диспетчеру автобус соседнего парка по ходу дня.

### POST /api/days/{day_id}/events/apply - применить вариант

```
{"event": {"type": "breakdown", "vehicle_id": "P07-V0038", "at": "08:40"}, "option": 1}
```

Сервер заново строит варианты на это событие (они детерминированы), применяет вариант с номером `option` и отвечает состоянием дня (раздел «Состояние дня») с полем `violations` из `check_state`. События применяются только по порядку времени: событие раньше последнего в журнале - 400.

### GET /api/days/{day_id}/edits/options - кого можно поставить

Параметры: ровно один из `duty_id` (автобусы) или `shift_id` (водители), и необязательные `from`, `to` - окно в виде ЧЧ:ММ. По умолчанию окно - всё время наряда или смены.

```
{"duty_id": "P07-R02-WD01", "from": "04:55", "to": "25:10", "total": 13, "shown": 13,
 "vehicles": [{"vehicle_id": "P07-V0197", "board_number": "7197", "class": "big"}, ...]}
```

```
{"shift_id": "P07-R01-WD01-S1", "from": "04:50", "to": "11:40", "for_vehicle": "P07-V0038",
 "total": 25, "shown": 25,
 "drivers": [{"driver_id": "P07-D0569", "tab_number": "070569", "own_vehicle": false}, ...]}
```

Список уже отфильтрован по нормам: автобус исправен, не выбыл, подходящего класса, из парка наряда или переброшен в него утром, свободен на всём окне. Водитель сегодня не работает, работает по графику, прошёл медосмотр, допущен к классу автобуса, который реально поведёт (`for_vehicle`), отдохнул после вчерашней смены, и окно не длиннее дневной нормы. Всё, что в списке, ставится без нарушений. Длинный список обрезан: `shown` показано из `total` найденных, не больше 50.

### POST /api/days/{day_id}/edits - ручная правка плана

Диспетчер ставит или снимает автобус (водителя) сам, не спрашивая движок.

```
{"type": "set_vehicle", "duty_id": "P07-R02-WD01", "vehicle_id": "P07-V0197",
 "from": "10:00", "to": "14:00", "reason": "автобус нужен на важном маршруте", "force": false}
```

| Поле | Что это |
|---|---|
| type | `set_vehicle`, `clear_vehicle` (нужен `duty_id`), `set_driver`, `clear_driver` (нужен `shift_id`) |
| vehicle_id, driver_id | Кого ставим. Для снятия не нужны |
| from, to | Окно правки, ЧЧ:ММ. По умолчанию - всё время наряда или смены. Вне его - 400 |
| reason | Причина для журнала, необязательно |
| force | Применить, даже если правка нарушает нормы. По умолчанию false |

Ответ - состояние дня (раздел «Состояние дня») плюс два поля: `violations` - все нарушения дня сейчас, `new_violations` - только те, что появились из-за этой правки.

**Правка, которая нарушает нормы, по умолчанию не применяется**: ответ 409, в теле `violations` со списком нарушений и `hint`. Состояние дня при этом не меняется. Повтор с `force: true` применяет правку и пишет в журнал `"forced": true` вместе со списком того, что нарушено, - решение диспетчера остаётся за диспетчером, но остаётся и в журнале. Нарушения, которые были в дне до правки, ей не приписываются.

Правка никогда ничего не пересчитывает: поставили - стоит. Что стоит в окне, тем правка и заменяется; то, что до и после окна, остаётся. Снятие на середину наряда оставляет в нём разрыв. В отличие от событий, правки не обязаны идти по порядку времени: диспетчер правит и то, что уже прошло, и то, что впереди.

Запись в журнале:

```
{"kind": "edit", "type": "set_vehicle", "duty_id": "P07-R02-WD01", "vehicle_id": "P07-V0197",
 "from": "04:55", "to": "25:10", "title": "Диспетчер поставил автобус 7197 на наряд P07-R02-WD01",
 "forced": false, "violations": [], "reason": "..."}
```

### POST /api/days/import - загрузить реестр перевозчика

Реестр перевозчика не совпадает с нашим форматом и не обязан. Эта ручка принимает его как есть: CSV текстом или книгу Excel в base64, узнаёт столбцы по названиям, переводит слова в коды и отдаёт **отчёт о загрузке** - что чем понято.

```
{
  "files": {"Автобусы": "Гаражный номер;Класс;Топливо;Парк;Тех. состояние\n7001;большой;газ;П7;исправен\n",
            "Водители": "...", "Парки": "...", "Маршруты": "...", "Наряды": "...", "Смены": "..."},
  "workbook": "<книга .xlsx в base64, вместо files или вместе с ним>",
  "meta": {"date": "2026-10-05", "day_type": "weekday", "moment": "morning"},
  "dry_run": false
}
```

| Поле | Что это |
|---|---|
| files | {название файла или листа: текст CSV}. Разделитель определяется сам: точка с запятой, запятая или табуляция. Не больше 24 файлов |
| workbook | Книга Excel (.xlsx) целиком в base64. Листы - те же сущности. Старый .xls не читается, его надо пересохранить |
| meta | Дата дня и тип дня обязательны: в реестре их нет, их задаёт тот, кто загружает. `moment` - `plan` или `morning` |
| dry_run | `true` - прочитать и отдать отчёт, день не создавать. Так интерфейс показывает «вот что я понял» до того, как что-то создано |

Ответ при удаче - как у `POST /api/days` (`day_id`, `date`, `counts`, `warnings`) плюс `report`. При `dry_run` `day_id` равен `null`. Если реестр прочитан с ошибками - 400, и в теле тот же `report`: он нужен именно тогда, когда что-то не вышло.

```
"report": {
  "entities": [{"entity": "vehicles", "source": "Автобусы", "rows": 420,
                "matched": {"board_number": "Гаражный номер", "condition": "Тех. состояние", ...},
                "defaulted": ["plate", "model", "repair_days_left", "home_route_id"],
                "derived": ["id"], "unknown_columns": ["Примечание"], "missing": []}],
  "errors": [...], "warnings": [...], "unknown_tables": ["Путевые листы"],
  "unknown_values": [{"entity": "drivers", "field": "medical", "value": "не прошёл", "rows": 12}]
}
```

| Поле отчёта | Что это |
|---|---|
| matched | Наше поле и столбец реестра, которым оно понято |
| defaulted | Столбца не было, поле заполнено само: движку оно не нужно либо нужно, но не обязательно |
| derived | Поле собрано из другого: кода автобуса нет - берём гаражный номер, кода водителя нет - табельный |
| unknown_columns, unknown_tables | Что пропущено, потому что не опознано. Это не ошибка, но посмотреть стоит |
| unknown_values | Значение, которое не удалось понять, и в скольких строках оно встретилось |

Три правила загрузки:

1. **Поле, от которого зависит решение движка, не выдумывается.** Нет столбца - ошибка, которая его называет. Это `id`, `name`, `state`, выпуск у парков; `id`, `park_id`, `number`, классы, важность, время оборота у маршрутов; все поля нарядов и смен; `id`, гаражный номер, класс, топливо, парк, состояние у автобусов; `id`, табельный номер, парк, допуск, график у водителей.
2. **Двусмысленное значение не угадывается.** «Не прошёл» у медосмотра - это недопуск или человек ещё не проходил? От ответа зависит, выпустим ли мы его на линию, поэтому такое значение уходит в `unknown_values`, а не толкуется. Список понятных слов - в `naryad/data/registry.py`, словарь `VALUES`; дополнять его по мере того, как видим живые реестры.
3. **Ошибка называет место.** Сущность, строка, столбец и само значение.

Что заполняется само и о чём пишется в отчёт: адрес и координаты парка, госномер и модель автобуса, ФИО водителя, источник длины маршрута, место начала смены (`park`). Списочное количество автобусов парка и число нарядов маршрута считаются по самим данным, иначе проверка нашла бы расхождение, которого в реестре нет. Срок ремонта неисправного автобуса ставится в 1 день: движок его не использует, он нужен только прогнозу на несколько дней. Закрепление автобуса за маршрутом и водителя за автобусом - предупреждение, движок без них работает, но не сможет ставить своего водителя на свой автобус. Отсутствие столбца с медосмотром при `moment: morning` - ошибка: утром на линию выпускается только водитель с пройденным медосмотром, и план вышел бы пустым без видимой причины.

Время читается в виде `Ч:ММ` и `ЧЧ:ММ`, часы после полуночи идут дальше 24. Из Excel время приходит долей суток, она переводится сама. Списки (классы, допуски) разделяются `|`, запятой, точкой с запятой или косой чертой.

То же из командной строки: `python -m naryad.data.registry <папка с CSV или файл .xlsx> --date 2026-10-05 --day-type weekday --out день.json`.
